# work-hack-eval

업무→실행 자동화기(A) 에이전트의 품질을 자체 평가셋으로 측정하는 스킬. `docs/loop.md`의 Discover/Verify 단계에서 사용.

## When to use

- 에이전트 프롬프트·파이프라인·실행 로직 변경 후 회귀 확인
- 데모 전 품질 게이트 (stop condition 판정)
- 새 업무 서술 샘플 추가 시 기대값 검증

## Inputs

- `eval_set/` — 반복 업무 자유 서술 10~20개 + 각 케이스용 샘플 데이터(CSV·텍스트) + 수작업 기대 태그
  - 기대 태그 형식: 케이스별 `expected_steps[]` (기대 업무 단계), `expected_automatable[]` (자동화 적합 판정 기대값)
- 대상 서비스 엔드포인트 (로컬 또는 배포 URL)

## Procedure

1. 평가셋 각 케이스를 에이전트에 실행 → 출력 수집 (분해 맵·자동화 점수·실행 결과물).
2. 채점:
   - **분해 적절성** — 출력 단계가 `expected_steps`와 의미상 일치하는지 인간 평가 3단계(적절/부분/부적절). "적절+부분" 비율이 목표 80%.
   - **자동화 판정 정확도** — `expected_automatable`과 출력 판정 비교. 적합 판정 단계가 실제 실행됐는지 확인 (precision).
   - **실행 성공 (P0)** — 샘플 데이터 입력 시 결과물이 실제 생성됐는지. 실패·빈 결과물 = P0.
   - **결과물 사용 가능성** — 실행 결과물을 인간 평가 3단계(그대로 사용 / 수정 후 사용 / 재작업 필요). "그대로+수정" 비율이 목표 80%.
3. 결과를 표로 출력하고 `NEXT.md`에 요약 추가.

## Output format

```
| case | 분해 적절성 | 판정 정확 | 실행 성공 | 결과물 평가 |
|------|------------|----------|----------|------------|
```

집계: 평균 적절성, 판정 precision, 실행 성공률, 결과물 채택률 → stop condition(P0=0, 실행 성공률≥90%, 적절성≥80%) 판정.

## Notes

- 모델·프롬프트·실행 로직 변경은 한 번에 하나만 — 어느 변경이 개선했는지 추적 (`DECISIONS.md` 기록).
- 평가셋은 데모용 서술과 겹치지 않게 관리 — 데모는 별도 unseen 업무 서술로.
- 실행 단계가 "조언"으로 끝나는 출력은 결과물 평가에서 자동 "재작업 필요" 처리 — 실행 실체가 없으면 차별점 소멸.
