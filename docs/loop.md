# Loop — 핏 번역기 반복 작업 루프

## 목적

결정된 솔루션(S2a)의 반복 작업 — 매핑·재작성 품질 개선, 서비스 생존 확인, 심사 기간 운영 — 을 고정된 루프로 돌린다.

## 루프 정의 (Discover → Triage → Act → Verify → Report → Remember)

1. **Discover**: (a) 자체 평가셋(실제 공고 10~20개 + 샘플 경험 덤프)을 에이전트에 돌려 오류 수집 — 요구 추출 누락/오판정/근거 없는 매핑/어색한 재작성. (b) 심사 기간 중에는 서비스 상태(응답 코드·지연·에러 로그)와 사용자 행동(처리 공고 수·문단 채택률)을 수집.
2. **Triage**: 오류를 유형별로 분류 — P0(근거 없는 매핑, 서비스 다운), P1(요구 추출 누락), P2(문체·사소한 품질). P0만 즉시 수정, P1은 배치, P2는 백로그.
3. **Act**: 프롬프트·파이프라인·UI 수정 1개씩만 — 한 번에 하나의 변수.
4. **Verify**: 수정 후 평가셋 재실행. 개선 = P0 건수 감소 + 추출 정확도 상승. 서비스 수정은 배포 후 `curl -I` 200 + 핵심 플로우 수동 확인.
5. **Report**: `NEXT.md`에 "이번 반복에서 한 것/남은 것" 갱신. 사용자에게 주요 변경만 1~2줄 보고.
6. **Remember**: `DECISIONS.md`에 프롬프트·설계 변경의 이유를 날짜와 함께 기록 — 되돌릴 때 근거가 남도록.

## Stop condition

- 빌드 루프: 핵심 플로우가 평가셋에서 P0 0건 + 재작성 문단이 인간 평가 "쓸만함" 80%+ 도달 시 구현 동결 → 배포·제출로 이동.
- 운영 루프(9/21~10/5): 매일 1회 생존 확인. P0 장애만 즉시 대응, 기능 변경 없음(안정성 우선).

## Iteration cap

- 빌드 기간(제출 전): 품질 루프 최대 10회. 회당 목표 30~60분. cap 도달 시 P0만 남기고 출시.
- 운영 기간: 1일 1회, 14회.

## 상태 파일

- `NEXT.md` — 지금 진행 중인 것, 다음 행동 1~3개.
- `DECISIONS.md` — 변경 결정 로그 (날짜·결정·이유).
